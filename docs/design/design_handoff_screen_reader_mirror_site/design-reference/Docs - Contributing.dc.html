Specs, fixtures, roadmap

Behaviour is decided in a spec before it is written in code, and every behaviour has a golden HTML fixture. That makes contributions small and arguments short.

Repository

One engine, thin hosts

packages/
  core/        the engine: linearize, roles, visibility, live regions, tests, fixtures
  extension/   MV3 host over core
  cli/         Playwright host over core; the bridge
  web/         the hosted demo
docs/
  specs/       SPEC-001 … one per behaviour
  decisions/   ADR-0001 … why things are the way they are
  design/      brief, handoff, these pages
  project/     roadmap and board
  • pnpm workspace. pnpm i, pnpm test, pnpm build.
  • Hosts import core; core imports nothing from hosts. Lint enforces it.

Specs and ADRs

Decide, then build

  • SPEC-001 reading order, roles, names, levels, flags, hidden content. SPEC-002 extension MVP. SPEC-003 shadow DOM, slots, frames. SPEC-004 live regions.
  • A spec has numbered acceptance criteria (AC-1 …). Tests cite the AC they cover; the API docs cite the spec a field comes from.
  • ADR-0001 infrastructure first, client-side only, no vendor lock-in. ADR-0002 MIT. ADR-0003 monorepo with a shared core.
  • Changing behaviour: amend or add a spec in a PR first, discuss there, then implement. Small fixes with an existing AC skip straight to code and a fixture.

Fixtures

One HTML file per behaviour

  1. 1

    Write the smallest HTML that shows it

    packages/core/test/fixtures/<area>/<name>.html, with a comment naming the spec AC.

  2. 2

    Write the expected list

    <name>.expected.json: the InterpretationNode[] it should produce. Run pnpm test:update to generate it, then read it line by line before committing.

  3. 3

    Check it against a real screen reader if you can

    Open the fixture with the bridge running (Testing with NVDA). Note the result in the PR; a known difference goes on Divergences.

Fixtures are never deleted. A behaviour that changes gets a new expected file and a changelog line under "Output changes".

Roadmap

In order

  • Shipped core 0.x: SPEC-001, 003, 004. npm and CDN.
  • Next extension MVP (SPEC-002): side panel, badge, settings, AX tree source.
  • Next CLI with --check, snapshots, reports.
  • Then profiles: NVDA first, then JAWS, VoiceOver.
  • Then the bridge and capture, NVDA first.
  • Then hosted demo with URL fetch and report import.

The board in docs/project/board.md is the live version. Pick anything marked "help wanted".
