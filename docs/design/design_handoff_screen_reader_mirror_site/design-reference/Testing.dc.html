Testing: seeing what a screen reader says

The engine computes one interpretation. Everything else is a question of where the tree came from, how it is phrased, how you are moving through it, and what a real screen reader said at the same moment. Those four things become four visible controls, in that order, above every Spoken list.

Journey C0

Set up, step by step

You need three things on one Windows computer: NVDA (the screen reader), Node (to run the bridge), and the mirror in whatever form you like. Each step says what to type, what you should see, and what to do if you do not see it. Fifteen minutes the first time.

1

Install NVDA

NVDA is the free screen reader this is built around. Get it from nvaccess.org/download. Run the installer, keep the defaults, let it start.

NVDA starts talking. Press Insert + N to open its menu, then Tools › Speech Viewer. A small window shows every word it says as text.

You should see the Speech Viewer window fill with text as you move around. Leave it open; the bridge reads from it.

If not: NVDA may be muted. Insert + S cycles speech mode; pick "talk". Or check the sound output.

2

Install Node

Node runs the bridge. Get the LTS version from nodejs.org, run the installer, keep the defaults. Then open a terminal: press Windows, type terminal, Enter.

> node --version v22.11.0

You should see a version starting with v20 or higher.

If not: close the terminal and open a new one; the installer only reaches new windows. Still nothing: restart the computer.

3

Start the bridge

In that same terminal, type one line. The first run downloads the tool; later runs are instant. Leave this window open the whole time you test.

> npx screen-reader-mirror listen ● NVDA 2025.1 detected Bridge on ws://localhost:7331 Pair code 4 8 2 1

You should see the green dot, NVDA's version and a four-digit pair code. Write the code down.

If not: "no screen reader found" means NVDA is not running or Speech Viewer is closed; fix that and the line updates by itself. "EADDRINUSE" means 7331 is taken; add --port 7332.

4

Open the mirror and pair

Pick one. They all ask for the same code once.

  • Bookmarklet: open the page you want to test, click the "Mirror this page" bookmark. See d1.
  • Extension: click the sr icon, then "Open side panel". See d3.
  • CLI: a second terminal, npx screen-reader-mirror <url> --capture bridge --headed. See d4.
  • Package: for developers writing code. See d2.

You should see "Bridge found on this machine" and four boxes for the code (c2). Type it. The Capture pill turns green and says NVDA · live.

If not: no "Bridge found" means the terminal from step 3 closed, or the port changed; the panel has a field for the port. Wrong code three times: the terminal prints a new one.

5

Press keys, read both columns

Click once inside the web page so NVDA is reading it, then press ↓ to move one item at a time. The left column is what the mirror expected. The right column fills with what NVDA actually said.

match the same thing. Good.differs two different strings. Read both; report it with the button if the mirror is wrong.extra NVDA said something the mirror has no row for ("clickable"). Normal.not reached yet you have not got that far. Keep pressing.

Try next: press H to jump between headings and switch Mode to Headings (c4); press Tab and switch to Tab order (c5).

When done: Ctrl+C in the bridge terminal. Nothing was sent anywhere; the pairing is remembered for next time.

Mac

VoiceOver instead of NVDA

Skip step 1; VoiceOver is built in (Cmd + F5). The bridge reads its captions panel. Steps 2 to 5 are the same; the Profile pill says VoiceOver and there is no forms mode.

No bridge

Just want to look?

Skip steps 2 to 4. Open the mirror on any page; the left column works alone. Add NVDA later when you want to check the mirror against the real thing.

Two computers

Tester here, developer there

The bridge only talks to the same machine. The tester saves the session report (step 5, Ctrl+C) and sends the JSON; the developer imports it as a log (c12).

Journey C1

Live capture through the bridge

The CLI runs a small local bridge that listens to a running screen reader (NVDA's speech output on Windows, VoiceOver's spoken text on macOS) and republishes each utterance on localhost. The extension side panel and the CLI report subscribe. Nothing leaves the machine.

1

Start the bridgec1

One command. It detects the screen reader, prints the port and waits. Without a screen reader running it says so and keeps waiting.

Terminal

Journey C4

NVDA beside the DOM walk, on every install

The DOM walk is the source every host has, and NVDA is the screen reader most testers run. So the pairing that matters most is DOM walk + NVDA through the bridge, and it must work the same way whether the mirror arrived as a bookmarklet, a package, an extension or the CLI. One bridge, one pair code, one side-by-side layout. Only the frame around it changes.

Edge cases

States the storyboard must cover before it becomes clickable

Bridge

No screen reader running

Bridge starts, prints "no screen reader found, waiting" and polls. Panel Capture pill reads "Bridge found · no speech yet". Nothing is flagged until the first utterance arrives.

Bridge

Bridge not found

Capture pill shows "Not connected" with the one-line command to start it and the import-a-log fallback. Never a blank column.

Bridge

Wrong pair code · stale pairing

Three attempts, then the bridge prints a fresh code. A remembered pairing that fails once is dropped and asked again.

Alignment

More utterances than rows

NVDA says "clickable" or "visited" extra. Extra utterances attach to the nearest row as a sub-line marked "also said", not as a divergence.

Alignment

Fewer utterances than rows

The tester did not get that far. Unreached rows dim with "not reached yet"; the footer counts them separately from "differs".

Alignment

Order differs

Same strings, different sequence (CSS order, focus trap). Both columns keep their own order; a connector line crosses, and the row gets "order differs".

Mode

Mode key pressed while the page has focus

In Capture, the panel listens to the bridge, not the keyboard: the real key moves the real screen reader, and the panel follows what was spoken. Without Capture, keys are mapped by the panel.

Mode

Profile without the mode

VoiceOver has no forms mode, JAWS has no "D" for landmarks by default. The pill stays visible but disabled with the reason, so the list does not silently mean something else.

Source

Debugger permission refused

Stay on DOM walk; the AX pill shows "needs permission" on hover. Rows that are known to differ between the paths (closed shadow roots, layout tables) get a faint "verify with AX tree" note.

Source

Cross-origin frame

One row, "document · unreachable". In Capture the real screen reader does read it, so the right column fills where the left is empty, marked "inside frame", not "differs".

Source

Page re-renders mid-session

Re-run on change is on by default. The list keeps row identity by ref, so the live column stays attached; rows that vanished strike through for one run.

Log

Unrecognised log shape

Treated as one utterance per line, shown as "Plain text · 14 lines" with a prompt to pick the screen reader. Timestamps, if present, enable the live-region timeline.

Privacy

What the bridge sees

Only speech text and timestamps. No page URL, no DOM. Pairing and port are local. The settings sheet states this next to the Capture toggle.

Reporting

Report divergence

Pre-fills an issue: engine row, screen reader row, profile, source, versions, the selector and the minimal HTML around it. The user reviews before anything leaves the machine.
